# RAG 相关面试题

这篇已经从原始知识点整理成面试卡片格式。图片仍保留在 Obsidian 中，但面试 Agent 应优先使用这里的文字内容。

## 1. 什么是 RAG？

### 考点

- 是否理解 Retrieval Augmented Generation 的核心价值
- 是否知道 RAG 的边界，而不是把它当成万能增强
- 是否能说清 RAG 和模型本身能力的关系

### 核心理解

RAG 是 Retrieval Augmented Generation，也就是检索增强生成。它让大模型在回答前先从外部知识库检索相关资料，再把检索结果作为上下文交给模型生成答案。

RAG 适合解决三类问题：知识需要更新、知识在私有库里、回答需要引用依据。但它不能直接改变模型的推理能力，不能保证 100% 正确，也不能天然解决输出风格问题。

### 面试回答

我理解的 RAG 是一种把外部知识接入大模型的工程方案。它不是训练模型，而是在推理时先检索相关文档，再让模型基于这些文档回答。这样可以让模型使用更新、更私有、更可追溯的知识。

它的典型场景是企业知识库问答、客服文档问答、代码库问答。它的边界也很重要：如果检索不到正确内容，模型仍然可能答错；如果上下文太多或质量差，也可能引入噪声。所以生产里的 RAG 重点不只是“向量库”，还包括 chunking、metadata、rerank、引用校验和评估。

### 工程例子

企业内部制度问答系统里，制度经常变化，不适合每次都微调模型。可以把制度文档清洗、切块、向量化后放进索引。用户问“年假怎么计算”时，系统先检索最新制度条款，再生成答案并附引用。

### 容易踩坑

- 说成“RAG 可以消除幻觉”。更准确是降低幻觉风险，但不能保证。
- 只讲向量数据库，不讲文档清洗、chunking、rerank、评估。
- 忽略知识新鲜度和权限控制。

### 追问

1. RAG 和微调怎么选？
2. 如果检索结果错了，模型会怎么样？
3. 如何评估 RAG 的答案是否忠实于资料？

## 2. RAG 的工作流程是什么？

### 考点

- 是否能区分离线索引和在线查询
- 是否知道每个阶段可能出问题的位置
- 是否能从工程链路角度描述 RAG

### 核心理解

RAG 通常分为索引阶段和查询阶段。

索引阶段：加载文档 -> 清洗文档 -> 切割文档 -> 向量化 -> 写入索引或向量数据库。

查询阶段：用户提问 -> query 处理或改写 -> 向量/关键词检索 -> rerank/filter -> 构造上下文 -> 模型生成 -> 引用/校验。

### 面试回答

RAG 的离线阶段负责把知识变成可检索的数据，在线阶段负责把用户问题映射到相关知识并生成答案。离线阶段重点是文档清洗、chunking、embedding 和索引；在线阶段重点是 query rewrite、retrieve、rerank、context build 和 generation。

我会特别强调 RAG 是一个链路系统，任何一环都会影响最终质量。比如 chunk 切得差会导致答案跨 chunk 丢失；embedding 不适合领域会召回差；rerank 缺失会让无关文档排在前面；prompt 没约束引用会让模型自由发挥。

### 工程例子

代码库问答中，索引阶段要按文件、函数、类和注释结构切分，而不是简单按固定字符切。查询阶段还可以用 metadata 限定语言、目录或模块，再用 reranker 对候选代码片段重排。

### 容易踩坑

- 只说“文档向量化后相似度搜索”，漏掉清洗、过滤和评估。
- 把 top-k 检索结果全部塞给模型，导致上下文噪声过多。
- 没有保存每次检索和生成的 trace，出问题无法复现。

### 追问

1. 为什么 RAG 要分离线索引和在线查询？
2. query rewrite 有什么用？
3. 你会在 trace 里记录哪些信息？

## 3. RAG 和微调有什么区别？

### 考点

- 是否能区分“接入知识”和“改变模型行为/能力”
- 是否能根据业务场景做技术选型
- 是否理解成本、新鲜度和推理延迟的 tradeoff

### 核心理解

RAG 是在推理时检索外部知识，让模型基于上下文回答。微调是通过训练改变模型参数，让模型学习特定风格、格式、任务模式或领域能力。

大多数知识库问答优先考虑 RAG，因为知识更新快、可引用、成本较低。微调更适合输出风格固定、任务格式固定、需要模型学习某种稳定能力的场景。

### 面试回答

我会从目标上区分：RAG 主要解决“模型不知道或知识需要更新”的问题；微调主要解决“模型不会按某种方式做”的问题。

如果是企业文档、政策、商品信息这类经常变化的知识，我会优先用 RAG，因为更新知识只需要更新索引。如果是客服话术风格、固定 JSON 输出、领域任务模式，可能考虑微调。实际生产里也可以组合：用微调或 prompt 规范模型行为，用 RAG 提供最新知识。

### 工程例子

金融研报问答适合 RAG，因为研报每天更新，并且答案需要引用来源。客服机器人如果要求固定语气、固定流程和特定格式，可以在 RAG 基础上再做指令微调或模板约束。

### 容易踩坑

- 认为微调能记住所有企业知识且永远准确。
- 认为 RAG 能让模型学会新的复杂推理能力。
- 忽略 RAG 的在线检索延迟和微调的数据维护成本。

### 追问

1. 什么情况下你会优先微调？
2. RAG 和微调可以一起用吗？
3. 如果业务要求低延迟，RAG 会有什么挑战？

## 4. RAG 中的文档切割策略怎么选？

### 考点

- 是否理解 chunking 对召回质量的影响
- 是否能根据文档结构选择切割策略
- 是否知道 chunk size、overlap 和语义完整性的 tradeoff

### 核心理解

文档切割是为了让检索单元既能被准确召回，又保留足够语义。常见策略包括固定大小切割、递归字符切割、基于标题/段落/代码结构切割、语义切割和 Agent 驱动切割。

起步阶段可以用 RecursiveCharacterTextSplitter，块大小 256-512 tokens，overlap 10%-20%。如果文档结构清晰，优先用结构化切割。对高质量要求场景，可以尝试语义切割，但成本更高。

### 面试回答

我不会只固定一个 chunk size，而是根据文档类型选。FAQ 和短文档可以按问答或段落切；技术文档适合按标题层级切；代码库适合按函数、类、文件结构切；长 PDF 可以先做版面和标题识别，再递归切。

chunk 太小会丢上下文，chunk 太大会引入噪声并降低匹配精度。overlap 可以缓解跨段信息丢失，但会增加索引体积和重复召回。最终要用 eval set 看 retrieval recall 和 answer quality，而不是只凭经验值。

### 工程例子

对 API 文档做 RAG 时，我会按 endpoint 或函数签名切块，并把 method、path、version、module 写入 metadata。这样用户问某个接口参数时，可以用 metadata filter 缩小召回范围。

### 容易踩坑

- 所有文档都按固定长度硬切。
- 只看 chunk 数量，不看语义完整性。
- 图片、表格、代码块没有转成可检索文字。

### 追问

1. chunk 太大和太小分别有什么问题？
2. overlap 多少合适？
3. PDF 表格内容怎么处理？

## 5. Re-rank 是什么？为什么需要它？

### 考点

- 是否理解 first-stage retrieval 和 second-stage reranking
- 是否知道 bi-encoder 和 cross-encoder 的区别
- 是否能说出 rerank 的成本和收益

### 核心理解

向量检索返回的结果不一定是最相关的。Rerank 是在第一阶段召回候选文档后，用更精细的模型重新排序，让最相关的内容排到前面。

第一阶段通常使用 bi-encoder，把 query 和文档分别编码成向量，速度快但交互弱。第二阶段常用 cross-encoder，把 query 和文档一起输入模型判断相关性，效果更好但速度更慢。

### 面试回答

Rerank 解决的是“召回结果排序不够准”的问题。向量检索适合快速从大量文档里捞出候选，但因为 query 和 doc 是分别编码的，它可能只捕捉粗粒度语义相似，不能很好理解细节匹配。

所以生产里常用两阶段检索：先用 embedding 或 hybrid search 召回 50-100 个候选，再用 reranker 精排出 top5-top10 给模型。这样能在质量和延迟之间平衡。

### 工程例子

用户问“如何重置企业微信 SSO 登录密码”，向量检索可能召回“微信登录失败”“SSO 配置”“密码策略”等多个文档。Reranker 能根据 query 和文档的细节交互，把真正讲重置流程的文档排到最前。

### 容易踩坑

- 只用 top3 向量检索结果，召回不足。
- 候选集过大导致 rerank 延迟太高。
- 没有用评估集比较加 rerank 前后的收益。

### 追问

1. Bi-encoder 和 cross-encoder 有什么区别？
2. 你会召回多少候选再 rerank？
3. Rerank 带来延迟时怎么优化？

## 6. RAG 答案不准，怎么排查？

### 考点

- 是否有分层排查思维
- 是否能区分 retrieval failure 和 generation failure
- 是否知道如何建立回归评估

### 核心理解

RAG 出错不要直接改 prompt，要先看 trace。核心判断是：检索结果里有没有正确答案。

如果没有，问题多半在文档、切块、索引、embedding、metadata filter、query rewrite 或召回参数。如果有但模型没答对，问题多半在上下文排序、prompt、引用约束、模型能力或输出校验。

### 面试回答

我会先固定一个失败样例，保存 query、检索结果、rerank 分数、最终 prompt 和模型输出。第一步看 top-k 文档是否包含正确答案。

如果正确答案没被召回，我会检查文档是否入库、chunk 是否切碎、metadata 是否过滤错、embedding 是否适合领域、top-k 是否太小，必要时加 hybrid search 或 query rewrite。如果正确答案已经在上下文里，但模型答错，就看 prompt 是否要求基于资料回答、上下文是否太长、相关片段是否被排在后面、是否需要引用校验。

最后把这个问题加入 eval set，作为回归测试。

### 工程例子

客服知识库里用户问“退款多久到账”，模型回答成“如何申请退款”。trace 显示 top5 只有申请流程，没有到账时效。排查发现“到账时间”在表格图片里没有 OCR 入库，所以修复方式不是改 prompt，而是补 OCR 和表格解析。

### 容易踩坑

- 只凭最终答案猜问题，不看检索结果。
- 一上来就改 prompt，掩盖 retrieval 问题。
- 没有把失败案例沉淀成 eval。

### 追问

1. 如果 top10 都不相关怎么办？
2. 如果 top10 有答案但模型仍答错怎么办？
3. RAG eval set 应该包含哪些 case？
