## 一、核心概念与考点

### FEISHU-AGENT-01-001：这一题在面试里到底考什么

考点：

- 能否说清 Agent 与普通 LLM、chatbot、workflow、function calling 的边界。
- 能否判断一个需求是否真的适合 Agent，而不是把所有大模型应用都包装成 Agent。
- 能否从工程视角解释 Agent 的自治程度、约束、终止条件和风险。

参考回答：

Agent 本质上是围绕目标运行的系统，而不只是一次输入输出的模型调用。它通常会在多步执行中基于观察结果动态决定下一步动作，并通过工具或外部环境持续推进任务。和普通 chatbot 相比，Agent 更强调目标驱动、多步决策、环境交互和状态持续；和 workflow 相比，Agent 的关键差异在于运行时具有更高的决策自由度，而不是所有步骤都预先写死。

是否应该引入 Agent，要看任务路径是否不确定、是否需要多轮环境交互、是否存在动态规划需求，以及引入自治后能否接受成本、延迟和风险。

追问：

- 如果一个系统用了大模型和工具，你怎么判断它是不是 Agent？
- 为什么很多场景里 workflow 比 Agent 更合适？
- Agent 的自治程度越高一定越好吗？

评分提示：

- 合格：能区分 Agent、chatbot、workflow。
- 优秀：能补充工程判断标准，包括任务不确定性、控制成本、终止条件和风险治理。

## 二、Agent 定义与组成

### FEISHU-AGENT-01-002：什么是 Agent：从会回答到会完成任务

考点：

- Agent 的定义。
- Agent 从“生成答案”到“推进任务”的变化。
- Agent 的最小组成要素。

参考回答：

Agent 是一种围绕任务目标运行、能够在执行过程中根据中间观察结果决定后续动作，并借助工具或外部环境持续推进任务完成的系统。它不只是回答问题，而是会把目标拆解成多个步骤，在执行过程中观察结果、调整策略、调用工具，并持续运行直到终止条件满足。

面试里可以用四个关键词展开：

1. 围绕目标运行：系统不是只响应一句话，而是为了达成一个明确目标。
2. 在执行过程中做决策：每一步可能根据环境反馈改变路线。
3. 借助外部能力推进任务：例如检索、数据库、API、代码解释器、浏览器或企业系统。
4. 持续运行直到终止条件满足：例如任务完成、达到预算、失败次数过多或需要人工确认。

Agent 的核心组件可以概括为：

1. Goal / Task：定义要完成什么。
2. Policy / Planner：决定下一步做什么，可以是模型、规则或混合策略。
3. Tools：连接外部能力。
4. State / Memory：保存中间状态、历史观察和必要记忆。
5. Guardrails / Governance：权限、边界、预算、人工确认和安全约束。
6. Evaluator / Verifier：检查结果是否满足目标。

追问：

- Agent 的终止条件一般怎么设计？
- Planner 一定要是大模型吗？
- 为什么生产 Agent 不能只靠 prompt？

评分提示：

- 合格：能说出目标、决策、工具、状态。
- 优秀：能补充控制约束和结果校验，并解释它们为什么是生产环境必需组件。

## 三、Agent 边界：什么不算 Agent

### FEISHU-AGENT-01-003：什么不算 Agent：边界比定义更重要

考点：

- 识别 Agent 的反例。
- 避免把所有 AI 应用泛化成 Agent。
- 能用“是否存在目标推进型运行循环”来判断边界。

参考回答：

不是所有使用大模型的系统都算 Agent。普通 chatbot 不一定是 Agent，因为它可能只是围绕用户输入生成一段回答，没有持续目标、状态和多步行动。固定流程的 workflow 也不一定是 Agent，因为它的步骤通常是预先确定的，运行时决策自由度很低。只有 function calling 也不足以构成 Agent，如果系统只是一次性选择一个工具并结束，它更像工具增强型聊天机器人。有记忆也不等于 Agent，记忆只是状态能力，不代表系统会围绕目标持续决策和行动。

判断标准可以压缩成一句话：是否存在围绕目标持续推进的运行循环，并且系统会根据中间观察结果动态决定下一步动作。

追问：

- 一个 RAG 问答系统算不算 Agent？
- 带 function calling 的客服机器人算不算 Agent？
- 只有长期记忆但没有工具调用，算 Agent 吗？

评分提示：

- 合格：能列出 chatbot、workflow、function calling、memory 的区别。
- 优秀：能用统一判断标准解释这些边界，而不是只背定义。

## 四、适用与不适用场景

### FEISHU-AGENT-01-004：为什么 Agent 会火：它到底解决了什么问题

考点：

- Agent 适合解决什么类型的问题。
- 为什么单轮 LLM 或固定 workflow 处理不了这些问题。
- 能否从任务路径、环境交互和上下文规模解释 Agent 的价值。

参考回答：

Agent 的价值不在于“看起来更高级”，而是在任务路径不确定、需要多轮环境交互、任务规模超过单轮上下文时，能够持续推进任务。

典型场景有三类：

1. 任务路径事先不确定：例如调研一个陌生技术方案，系统需要边查资料边决定下一步搜索方向。
2. 任务需要多轮环境交互：例如调用 API、读取文件、执行代码、根据结果重试或换策略。
3. 任务规模超过单轮上下文：例如长文档分析、代码库修改、复杂报告生成，需要分阶段处理和状态管理。

不适合 Agent 的场景也很明确：任务路径清晰、规则强、结果必须稳定可控、错误代价高且能通过规则系统解决时，workflow 或普通程序逻辑往往更好。

追问：

- 你会如何判断一个需求是否需要 Agent？
- 什么情况下强行 Agent 化会带来负收益？
- Agent 和 workflow 能否混合使用？

评分提示：

- 合格：能说出不确定、多轮交互、长任务。
- 优秀：能同时说清不适用场景，并体现成本、稳定性和风险意识。

## 五、自治程度

### FEISHU-AGENT-01-005：Agent 的自治程度：不要把全自动当成唯一答案

考点：

- Agent 自治程度是连续谱，不是二元开关。
- 能否根据任务风险选择 assisted、semi-autonomous、autonomous 或 open-ended。
- 能否理解“越自动”不等于“越好”。

参考回答：

Agent 不一定要完全自治。自治程度可以粗略分成四类：

1. Assisted Agent：以人为主，模型提供建议，工具执行仍依赖人工触发。例如 IDE 里的代码建议、审批流中的推荐决策。
2. Semi-Autonomous Agent：系统可以完成部分步骤，但关键节点需要人工确认。例如生成方案、检索资料、草拟邮件后等待确认发送。
3. Autonomous Agent：在明确目标、权限和终止条件内自动完成任务。例如自动整理数据、生成报告、提交低风险变更。
4. Open-Ended Agent：目标开放、运行时间长、环境变化多，通常需要更强的监控、权限治理和中断机制。

面试中要强调：自治是连续谱，不是二元开关。任务可以被拆成阶段，但阶段之间仍需动态协调；如果一个需求明明两段规则加一次检索就能解决，却硬做成多 Agent，只是为了看起来高级，反而说明缺少成本意识。

追问：

- 哪些操作必须 human-in-the-loop？
- 如果 Agent 执行到一半发现目标不清楚，应该怎么办？
- 你会如何限制高自治 Agent 的权限？

评分提示：

- 合格：知道 Agent 可以半自动。
- 优秀：能根据风险、权限、成本和可回滚性选择不同自治级别。

## 六、常见误区与纠偏

### FEISHU-AGENT-01-006：常见误区与纠偏

考点：

- 能否识别 Agent 设计中的常见误区。
- 能否把概念纠偏落到工程判断。

参考回答：

常见误区包括：

1. 用了工具就是 Agent。
   纠偏：工具增强型应用和 Agent 的区别，在于是否存在目标推进型运行循环，以及是否根据观察持续决策。
2. Agent 一定比 workflow 高级。
   纠偏：当流程清晰、规则稳定、错误代价高时，workflow 往往更可靠、成本更低。
3. Agent 就是把 prompt 写复杂。
   纠偏：Agent 工程还包括状态、工具、权限、观测、评测、恢复和终止条件。
4. 只要模型够强，就不需要工程约束。
   纠偏：模型越强，越需要明确边界、权限、审计和验证机制。
5. Agent 的核心是思维链。
   纠偏：生产系统更关注可执行动作、状态管理、工具可靠性和结果校验，而不是暴露或依赖思维链文本。

追问：

- 为什么“工具调用”不等于 Agent？
- 为什么很多 Agent demo 到生产会失败？
- 你会如何向业务方解释不要过度 Agent 化？

评分提示：

- 合格：能列举误区。
- 优秀：能说明误区背后的工程后果，比如不可控、成本高、难评估、难恢复。

## 七、Agent 最小运行闭环

### FEISHU-AGENT-01-007：Agent 的最小运行闭环是什么

考点：

- Agent loop。
- 观察、决策、行动、验证之间的关系。
- 终止条件与失败恢复。

参考回答：

Agent 的最小运行闭环可以概括为：

1. 接收目标：明确任务、约束、预算、权限和成功标准。
2. 规划或决策：决定当前最合适的下一步。
3. 执行动作：调用工具、查询资料、操作系统或生成中间产物。
4. 观察结果：读取工具返回、环境反馈或错误信息。
5. 更新状态：记录已完成步骤、上下文、失败原因和下一步候选。
6. 校验结果：判断是否达成目标，或者是否需要继续、重试、回退、升级人工。
7. 终止：在成功、失败、预算耗尽、风险触发或人工接管时停止。

追问：

- Agent loop 里最容易失控的是哪一步？
- 怎样避免 Agent 无限循环？
- 工具返回错误时，应该怎样把错误交给模型恢复？

评分提示：

- 合格：能说出 plan-act-observe。
- 优秀：能补充 state、verify、termination 和 recovery。

## 八、高频面试题与参考回答

### FEISHU-AGENT-01-Q01：什么是 Agent？和普通 LLM / chatbot 有什么区别？

分类：Agent 定义与边界

考点：

- Agent 的核心定义。
- Agent 与普通 LLM / chatbot 的差异。
- 工程上如何判断是否需要 Agent。

参考回答：

Agent 是围绕目标运行的系统，不只是一次输入输出的模型调用。它通常会在多步执行中基于当前观察结果动态决定下一步动作，并通过工具或外部环境持续推进任务完成。和普通 LLM / chatbot 相比，Agent 更强调目标驱动、多步决策、环境交互和状态持续。

工程上我会把 Agent 看成由目标、策略/规划、工具、状态/记忆、控制约束和结果校验组成的系统。是否应该使用 Agent，要看任务路径是否不确定、是否需要多轮环境交互，以及引入自治后能否接受成本、延迟和风险。

- 优秀：能自然补充状态、约束、校验和适用条件。

### FEISHU-AGENT-01-Q02：带 function calling 的聊天机器人算不算 Agent？

分类：Function calling 与 Agent 边界

考点：

- function calling 与 Agent 的关系。
- 一次性工具调用和持续决策循环的区别。

参考回答：

不一定。如果系统只是一次性选择一个工具然后结束，它更像 tool-augmented chatbot；如果系统会根据工具结果持续决策、多步推进任务，那就更接近 Agent。

比如用户问“今天北京天气怎么样”，模型调用一次天气 API 后回答，这只是工具增强问答。可是用户让系统“帮我规划一个三天北京行程，并根据天气、预算、景点开放时间持续调整”，系统需要多轮检索、比较、规划、修正和生成结果，这就更接近 Agent。

追问：

- function calling 在 Agent 里主要解决什么问题？
- 工具调用失败时 Agent 应该怎么恢复？
- tool-augmented chatbot 和 Agent 的测试重点有什么不同？

评分提示：

- 合格：能回答“不一定”。
- 优秀：能用是否存在持续目标推进和观察后再决策来判断。

### FEISHU-AGENT-01-Q03：Workflow 和 Agent 的区别是什么？

分类：Workflow 与 Agent 边界

考点：

- 固定流程和动态决策的区别。
- 什么时候 workflow 更合适。
- 什么时候 Agent 更有价值。

参考回答：

Workflow 更像预先定义好的流程，步骤、分支和执行顺序通常在设计时就确定了，适合规则稳定、路径清晰、结果要求可控的任务。Agent 更像运行时围绕目标动态推进的系统，它会根据中间观察结果决定下一步动作，适合路径不确定、需要多轮环境交互或需要动态规划的任务。

我不会把 Agent 看成 workflow 的高级替代品。很多生产任务用 workflow 更稳定、更便宜、更容易测试；Agent 适合放在路径不确定、需要模型判断和工具交互的部分。实际工程里常见做法是 workflow 管外层流程，Agent 负责某些动态子任务。

追问：

- 为什么 Anthropic 等实践里会强调能用 workflow 就不要过度 Agent 化？
- workflow 里能不能嵌入 Agent？
- Agent 里能不能有固定步骤？

评分提示：

- 合格：能说出 workflow 固定、Agent 动态。
- 优秀：能说出混合架构和选择标准。

### FEISHU-AGENT-01-Q04：Agent 一定需要工具吗？

分类：Agent 组件

考点：

- 工具是不是 Agent 的必要条件。
- 工具在 Agent 中的作用。
- 外部环境交互与任务完成能力。

参考回答：

严格说，Agent 不一定必须有外部工具，但生产语境下大多数有价值的 Agent 都会使用工具。因为 Agent 的核心不是“会调用工具”，而是“围绕目标持续决策并推进任务”；工具只是让它能和外部世界交互，比如检索、数据库、API、文件系统、代码解释器或浏览器。

如果一个系统没有工具，但能在内部状态中持续规划、检查和推进目标，也可以具备 Agent 特征。不过从工程价值看，没有工具的 Agent 往往能力边界很窄，更像复杂推理或多轮生成系统。

追问：

- 只有 memory 没有 tool 的系统算 Agent 吗？
- 工具 schema 设计会怎样影响 Agent 可靠性？
- 你会如何给高风险工具加权限控制？

评分提示：

- 合格：能说出工具常见但不是唯一判断标准。
- 优秀：能区分“工具调用能力”和“目标推进循环”。

### FEISHU-AGENT-01-Q05：什么时候你不会建议上 Agent？

分类：适用场景判断

考点：

- Agent 的反适用场景。
- 成本、稳定性、风险和可控性的工程权衡。

参考回答：

当任务路径清晰、规则强、结果必须稳定可控、错误代价高且可以通过规则系统解决时，我更倾向于 workflow 或纯程序逻辑。

比如发薪、扣款、权限审批这类高风险动作，如果规则明确，就不应该让 Agent 自主决定。再比如一个固定表单处理流程，用普通程序或 workflow 就能稳定解决，强行引入 Agent 只会增加成本、延迟、不可解释性和测试难度。

追问：

- 如何向业务方解释“不建议 Agent 化”？
- 哪些风险可以通过 human-in-the-loop 降低？
- 什么场景可以先用 workflow，后续再逐步 Agent 化？

评分提示：

- 合格：能说出路径清晰、规则强、不适合 Agent。
- 优秀：能补充错误代价、可测试性、可控性和业务沟通。

### FEISHU-AGENT-01-Q06：为什么大家总说 Agent 难做？

分类：Agent 工程难点

考点：

- Agent 难点不只是模型推理。
- 工具可靠性、上下文、权限、长任务、终止条件、评测和回放。

参考回答：

难点不在于让模型想一步，而在于如何在复杂环境里持续正确做事。Agent 会面对工具可靠性、上下文污染、权限控制、长任务恢复、终止条件、评测与回放等问题。

例如工具接口可能超时或返回脏数据，模型可能误解工具结果，长任务中上下文可能越来越乱，高风险动作需要权限和审计，任务失败后还需要能恢复或回放。生产 Agent 的重点不是让 demo 跑通一次，而是让它在大量真实场景中稳定、可观测、可限制、可评估。

追问：

- 怎样避免 Agent 无限循环？
- Agent 失败后你希望 trace 里记录哪些信息？
- 为什么 Agent eval 比普通问答 eval 更难？

评分提示：

- 合格：能列出工具、上下文、权限、长任务。
- 优秀：能讲到观测、回放、评测和失败恢复。

### FEISHU-AGENT-01-Q07：Agent 的核心组件有哪些？

分类：Agent 架构

考点：

- Agent 的最小工程组成。
- 每个组件的作用。
- 生产环境中不可缺少的控制与校验。

参考回答：

我会把 Agent 的核心组件概括为六块：目标、策略/规划、工具、状态/记忆、控制约束、结果校验。这六块缺一不可，尤其在生产环境里。

目标定义系统要完成什么；策略/规划决定下一步做什么；工具连接外部能力；状态/记忆保存中间结果和上下文；控制约束负责权限、预算、边界和人工确认；结果校验判断任务是否完成、是否需要重试或停止。

### FEISHU-AGENT-01-Q08：Agent 和 RAG 的关系是什么？

分类：Agent 与 RAG

考点：

- RAG 是知识增强方式，Agent 是任务推进范式。
- RAG 可以作为 Agent 的工具或子能力。
- 不是所有 RAG 都需要 Agent 化。

参考回答：

RAG 和 Agent 不是同一层概念。RAG 主要解决“如何把外部知识检索进上下文，让模型回答得更准”的问题；Agent 主要解决“如何围绕目标持续决策、调用工具并推进任务”的问题。

RAG 可以成为 Agent 的一个工具或子能力，比如 Agent 在调研、问答、代码理解时调用检索系统获取资料。但一个普通知识库问答系统不一定是 Agent，如果它只是检索一次再回答，就更像 RAG chatbot。反过来，Agent 也不一定必须包含 RAG，可能只调用业务 API 或文件系统完成任务。

面试里要强调：不是所有任务都值得 Agent 化，过度 Agent 化是常见反模式。

追问：

- RAG chatbot 什么时候会升级成 Agent？
- Agent 使用 RAG 时如何避免检索结果污染上下文？
- Agent 的 memory 和 RAG 知识库有什么区别？

评分提示：

- 合格：能说出 RAG 和 Agent 不是一回事。
- 优秀：能说出 RAG 作为 Agent 工具、以及过度 Agent 化风险。
